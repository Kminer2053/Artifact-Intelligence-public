# 1층 온톨로지 (ontology.json)

문서지능은 문서 제작을 4층으로 나눈다 — 1층 규칙·지식(이 온톨로지), 2층 설계(빌드플랜), 3층 인스턴스(맥락 자료를 넣은 문서 JSON), 4층 결과물(HTML·PDF·HWPX·PPTX). 이 폴더는 **1층 = 규칙/지식**이다. 하나의 파일, 개체 × 3요소 구조.

## 핵심 구조: 개체를 조회하면 3요소가 함께 나온다

```
entities.본문
├─ 구성(Structure):   개조식 위계, 유형별 목차, □3~5개…
├─ 문체(WritingStyle): 명사형 종결, 45자, 치환사전…
└─ 디자인(Design):    □○-* 마커·CSS·pt, 양쪽맞춤, 내어쓰기…
```

하나의 개체(예: 본문)가 **구성·문체·디자인 3요소 렌즈를 동시에 통과**한다. 이것이 이 프로젝트의 핵심 사상 — 3요소를 따로 파일로 쪼개지 않고, 개체에 3요소를 매단다.

## 파일 구성 (하나의 온톨로지, 주요 최상위 키)

| 키 | 내용 |
|---|---|
| `_model` | 이 온톨로지의 자기 설명(개체 정의·층 경계·근거 원칙) |
| `document_types` | 문서유형별 전역 방법론(여백·분량예산·위계체계·게이트·목차로직). 6장르: 1페이지 보고서(`onepage-report`)·풀버전(`fullreport`)·시행문(`gongmun`)·규정(`regulation`)·보도자료(`press-release`)·발표 슬라이드(`slides`). |
| `entities` | **개체 카탈로그** — 제목·요약박스·본문·붙임. 각각 구성/문체/디자인. |
| `data_elements` | 데이터에 따라 등장하는 요소(표·이미지). 개체 아님. 3층에서 등장 판단. |
| `writing_profiles` | 문체 프로파일(공문서-개조식). 문서유형이 참조. |
| `shared` | 공통 방법론(강조 num/delta/accent·표기 규범). 여러 개체가 참조. |
| `장르판별` | 요청 말·자료로 장르를 정하는 차례와 신호. |
| `_미확정_갈래` | 아직 재지 못했거나 더 모아야 정할 수 있는 갈래(규칙으로 쓰지 않는다). |

## 같은 폴더의 파일

| 파일 | 내용 |
|---|---|
| `ontology.json` | 규칙 원본(정본). 아래 설명이 모두 이 파일 이야기다. |
| `실측_타이포.json` | 공공보고서 실물에서 잰 글꼴·크기·줄간격·여백 값. 값은 `research/corpus/pattern.py` 가 쓰므로 손으로 고치지 않는다. 원문을 공개하지 않은 표본(규정·내부보고)은 표본 수와 손으로 적은 정성 요약만 싣고 문서별 분포는 싣지 않는다(다시 재도 요약은 그대로 둔다). |
| `파급표.json` | 규칙이 바뀌면 어디까지 미치는가 — 같은 규칙이 복제된 자리(조립기·게이트 등)의 지도. 규칙 하나를 고칠 때 함께 고칠 곳을 찾는 데 쓴다. |
| `editor-profiles.json` | 인라인 편집기가 읽는 장르별 개체·동작 선언. 편집기 코드는 하나이고 이 표만 갈아 끼운다. |
| `review.html` | 1페이지 보고서 방법론·개체·데이터 요소·문체·공통 규칙을 사람이 읽고 판정하도록 펼친 화면. `python3 render_review.py` 로 다시 만든다(밑줄로 시작하는 키는 싣지 않는다). |

## 개체 vs 데이터 등장요소 (중요)

- **개체**(제목/요약박스/본문/붙임): 문서 골격. 무엇이 들어갈지는 문서유형이 정함.
- **데이터 등장요소**(표/이미지): 맥락 데이터를 봐야 등장 여부가 정해짐. 2층 설계가 미리 못 박지 않고, 3층에서 판단.
- **□·○·-·\***: 개체가 아니다. 본문 개체가 개조식 방법론을 적용한 **결과로 나오는 내부 구조**. 그래서 entities.본문.디자인.위계_스타일에 들어있다.

## 층 경계 (이 온톨로지가 정하는 것 / 안 정하는 것)

- 정함: "개체가 무엇이고, 어떤 3요소 방법론을 갖는가"
- 안 정함: "본문에 □ 몇 개·○ 몇 개, 표를 쓸지" → 맥락 데이터가 들어온 **3층**에서 결정

## SSOT 관계

**ontology.json이 정본이다.** `references/*.md`는 이 온톨로지의 "사람이 읽는 뷰"로 만들었지만, 그 뒤 ontology.json 이 바뀐 만큼 다시 뽑지는 않았다. 둘이 다르면 ontology.json 을 따른다. 사람이 읽는 규칙은 규칙마당(https://rules.artifact-intelligence.app)의 카드로 본다. 카드는 온톨로지를 사람 말로 옮긴 것(227장)이라 온톨로지 전부를 담지는 않는다 — 슬라이드 v2(부품 트리) 규칙처럼 카드가 아직 없는 갈래가 있고, 카드와 온톨로지가 다르면 온톨로지를 따른다. 카드 자료와 경량 규칙 스킬 zip 은 `rules/build.py` 가 만든다.

## 근거 원칙

모든 규칙에 `근거`(출처 규칙 ID: R구-XX/R레-XX/교차대조맵 C-XX 등) 필수. 근거 없는 규칙은 등재하지 않는다.

## 소비 상태

지금은 파이프라인이 이 파일을 직접 읽는다. 설계 지시문(`composeplan`)·작성 지시문(`compose`)·장르 판정·목차 시퀀스·조립기의 일부 기준값(풀버전·슬라이드 카탈로그·표 프리셋)이 여기서 나온다. 웹앱·플러그인·MCP 가 같은 파일을 쓴다. 플러그인은 0.4.0부터 이 폴더를 설치본에 함께 싣고, 규칙 조회(`지식`)도 설치본 안의 이 파일을 로컬에서 읽는다(정책서버는 이 파일이 없을 때만 쓰는 예비다).
