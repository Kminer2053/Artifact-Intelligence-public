## 1. 1p 분량 예산 — 개수로 잡아라 (줄수·mm 아님)

**1차 생성자가 직접 제어하는 것은 "항목 개수"다.** 줄수·mm는 렌더를 돌려야만 나오므로 생성 시점에 못 쓴다. 아래 개수 예산을 지키면 대부분 1차에 1쪽에 든다. (예산의 실측 근거는 §1-1.)

- **□ 대제목: 4개** (3~5 허용, 5개 초과 시 풀버전 전환 검토)
- **표 없는 문서**: 본문 개조식 항목(○ + - + * 합계) **안전 18개 / 상한 20개**로 시작.
- **표 있는 문서**: (본문 항목 + 표 행수) 합계 **안전 16 / 상한 17**로 시작. 표는 행수 외에 캡션·상하 여백이 붙어 실측상 행수보다 ~2~3 유닛을 더 먹으므로, 무표 예산(20)보다 낮게 잡는다.
  - 예) 5행 표(헤더+4행)면 → 본문 항목 **11~12개** (11+5=16 안전 / 12+5=17 상한).
- 전제(둘 다 자동 적용됨): ○ 항목은 **45자 이내 1줄**(→ `writing-rules.md`), 줄간격 150%·자간 -0.045em은 CSS·jachigan.js가 담당. **○ 항목이 45자를 넘어 2줄이 되면 항목 2개로 계산**한다(개수 예산의 유일한 함정).

### 1-1. 개수 예산의 실측 근거
통과 확정 문서(headless Chrome 인쇄, 내장 Pretendard) 역산. 전 문서 □=4 고정.
- **무표**: 최대 부하 항목 20개(○14+-4+*2)에서 통과 → 상한 20, 안전 18.
- **유표**: 본문12+표5행=17 통과 / 본문13+표5행=18 실패(253mm, 인쇄영역 252mm를 ~1mm 초과) → **상한 17, 안전 16**. 무표(20)와의 차(≈3)가 표의 캡션+wrapper 여백 오버헤드다.
이 개수 모델이 mm 수식보다 생성자에게 직접적이다. 다만 상한은 경계값이므로 안전 목표(무표 18·유표 16)를 조준해야 "재압축 0회"가 안정적으로 달성된다.
[근거: prototype 13종 게이트 역산 + test/e2e-result-A/v2 실측(유표 17/18 경계 확인) + build/audit.js `contentMm`/`fillRatio`]

### 1-2. 최종 판정은 개수가 아니라 렌더
개수 예산은 **1차 생성 조준용 근사**다. 확정 판정은 항상 `bash build/render_verify.sh`의 `pages==1`이다. 개수를 지켜도 긴 문장·표가 많으면 초과할 수 있으니, 생성 후 반드시 게이트를 돌리고 실패 시 §3으로 압축한다.

## 2. 위계 구조 예산

- □ 대제목 **3~4개**
- □ 1개당 ○ 항목 **2~4개**
- 위계 깊이 **최대 4단** (□ → ○ → - → *)
- 체계 A(행정·실무/1p·메모) 전용: `□`16pt굵게 → `○`15pt → `-`14pt → `*`13pt회색 → `※`13pt. 체계 B(시행문·풀버전용 Ⅰ./1./가.)와 혼용 금지
  [근거: 06_repo-레이아웃규칙.md R레-08, R레-09, R레-10]
- 글상자(요약 음영박스) 내부는 이 위계를 쓰지 않는다 — 무마커 문장형이 기본, 나열이 필요하면 본문과 겹치지 않는 ◇·◈ 계열만 사용

## 3. 초과 시 압축 순서

분량 초과 시 아래 순서대로, 한 단계씩 적용하고 매 단계마다 재게이트(블록 높이 재측정)한다. 상위 단계에서 예산 내로 들어오면 하위 단계는 건드리지 않는다.

| 순서 | 대상 | 조치 |
|---|---|---|
| ① | `*` 참고 | 부가설명·비고성 `*` 항목 삭제 |
| ② | `-` 세부 | 하위 `-` 세부 항목을 상위 `○`에 통합(문장 병합). **단 병합 결과가 45자를 넘으면 병합하지 말고 그 `-` 항목을 삭제**한다(45자 규칙이 병합보다 우선 — 규칙 충돌 시 45자 승) |
| ③ | `○` 유사 | 내용이 겹치거나 인접한 `○` 항목끼리 병합 |
| ④ | 표 | 표 행 축소(유사 행 통합·비핵심 열 제거) |
| ⑤ | 어휘 | 동의어·군더더기 압축(`~할 것으로 보입니다`→`~예상`, `-적/-의/-것/-들` 정리 등) |

- 5단계를 모두 적용해도 초과하면 1p 양식이 아니라 풀버전 보고서로 양식 변경을 권고한다.
  [근거: 06_repo-레이아웃규칙.md R레-07 — 유사 순서(부가설명 제거→비고 후순위 제거→동의어 압축→조사·접미사 정리→풀버전 전환 권고)를 1p 위계(□○-*)에 맞춰 재정렬]
- 압축은 항상 문장을 짧게 만드는 방향으로만 쓴다. 자간을 추가로 좁히거나 폰트 크기를 줄여 물리적으로 우겨넣는 것은 압축 순서에 포함하지 않는다 — 자간 사냥꾼(jachigan.js)은 어절 잘림 방지용 미세조정이지 분량 확보 수단이 아니다.
  [근거: README "자간 사냥꾼 v2/v3" 항목 — 줄 단위 미세압축이지 콘텐츠 축약이 아님]

## 4. 분량 하한 — 상한과 같은 단위(채움도)로 판정

상한(1p 초과)뿐 아니라 **하한**도 있다. 하한과 상한을 다른 단위(하한=줄수, 상한=mm)로 재면 서로 어긋난다(종단 검증에서 "13줄인데 297mm 꽉 참 → 하한 위반인지 아닌지 판단 불가" 문제 발생). **하한도 상한과 동일하게 렌더 채움도로 판정한다.**

- **판정 지표**: `build/audit.js`가 보고하는 `fillRatio`(콘텐츠 하단 ÷ 인쇄영역)와 `sparse` 플래그.
  - `sparse == true`(fillRatio < **0.72**) → 하단 여백 과다, 보강 대상.
  - 적정: fillRatio **0.80~1.00**. 1.00에 가까울수록 꽉 참(1p 이상은 §3으로 압축).
- **개수 기준 조준값**: 본문 항목(+표행) 합계 **16~20개**를 1차 목표로. 14개 미만이면 대개 sparse가 뜬다.
- `sparse` 보강 순서(상위 항목부터 채운다):
  1. `○` 항목에 근거·배경 1문장 추가(빈 `-` 세부 채우기)
  2. 비고성 `*` 항목 추가(§3 압축 대상이므로 남발 금지)
  3. 표가 있다면 비교 행 추가
- 하한 미달을 폰트 확대·자간 확장·줄간격 확대로 채우지 않는다 — §1 렌더 전제(150% 줄간격·-0.045em 자간)를 깨뜨려 다른 문서와 판형이 어긋난다.
  [근거: README "13종 전수 검증" 잔여 — "분량 하한 게이트 필요"; test/e2e-result-A.md #2 — 하한/상한 단위 불일치. audit.js `fillRatio`/`sparse`로 통일 해소]

## 5. 45자 초과 문장 분리 우선순위

- 임계값(본문 11pt·42,520 HWPUNIT 폭 기준): **35자 이하** 안전 유지 / **36~45자** 검토 대상(자동 표시만) / **46자 이상** 자동 분리 후보(반드시 처리)
  [근거: 06_repo-레이아웃규칙.md R레-01]
- 46자 이상 또는 한 문장에 정보 2개 이상 혼재 시, 아래 순서로 분리한다(순서대로 시도, 앞 단계로 해결되면 중단):
  1. **및/쉼표 기준 분리** — 동등 항목 나열일 때 가장 자연스러움
  2. **종결어미 전환** — `~하고, ~하며, ~한 후` 등 연결어미를 종지부(`~함`, `~다`)로 바꿔 문장을 끊음
  3. **부사절 기준 절단** — `~으로 인해, ~에 따라` 등 부사절 경계에서 절단
  4. **개조식 항목화** — 위 방법으로도 안 되면 `-` 글머리 항목으로 쪼갬(정보 단위별로 항목 분리)
  [근거: 06_repo-레이아웃규칙.md R레-02 — ①의 자연스러움은 원문 명시, ②~④ 순서는 명시규칙(개별 근거 없음)]
- 예시: "라마단 종료…" 66자·정보 3개 혼재 → 3개 개조식 항목으로 분리(원문 예시)
